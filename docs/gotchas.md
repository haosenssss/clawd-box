# 实测踩坑记录

只记**实际踩到并验证过**的坑，以及确定的解法。不记推测。

---

## 1. macOS 串口：设备一关，termios 设置就丢

**现象**：`stty -f <port> 115200 raw` 配好后再写数据，板子只收到 250 字节里的 **1 字节**。

**原因**：`stty -f` 配完就关闭了设备。macOS 上串口设备**最后一个 fd 关闭时，termios 参数恢复默认**（回到 9600 之类）。随后 shell 的 `>` 重定向再打开，用的是默认参数，于是绝大部分字节在错误波特率下变成噪声。

**解法**：**先用 `openSync` 拿住一个 fd，再让 stty 去配这个"已经打开"的设备**，然后通过同一个 fd 写。只要我们的 fd 不放，设置就一直有效。

```ts
const fd = openSync(port, 'r+')   // ① 先拿住
await configurePort(port)          // ② stty 配的是已打开的设备
writeSync(fd, line)                // ③ 通过同一个 fd 写
```

顺序颠倒就会复现该问题。见 `host/src/serial.ts`。

## 2. 刚打开串口，头几个字节必丢

**现象**：坑 1 修好后，写 4 帧只有后 3 帧生效，**永远是第一帧（最长的那个）丢失**。表现为"会话存在但没有名字、状态是默认值"——很容易误判成解析 bug。

**原因**：CH343P 在设备打开瞬间会拨动 DTR/RTS，线路稳定前发出的字节收不全。

**解法**：打开后 `tcflush` 并静默 **300ms** 再开始发送。实测低于 200ms 仍会丢。因为守护进程会持续持有串口，这个代价只在连接时付一次。

---

## 3. `LINE_MAX` 是 POSIX 保留宏

`#define LINE_MAX 512` 不会报错，但会被 `limits.h` 里的同名宏悄悄覆盖/冲突，实际用的是系统值。**编译能过，行为不对。**

改用带前缀的名字，如 `LINK_LINE_MAX`。

---

## 4. 不要在 `link_start()` 里改 UART0 波特率

板子的日志和数据链路共用 UART0。若在 `uart_param_config()` 里设一个与控制台配置不同的波特率，日志会**从某一行开始突然变乱码**——现象非常像崩溃或死锁，实际只是收发两端不一致。

链路波特率一律由 `CONFIG_ESP_CONSOLE_UART_BAUDRATE` 决定，`link_start()` 只装驱动、不碰参数。

> 顺带：**115200 完全够用**。帧约 100 字节、每秒最多几帧，115200 提供 11.5 KB/s。
> 921600 在这里买不到任何东西，反而带来 macOS 上 `IOSSIOSPEED` 不可靠的麻烦
> （Python `termios` 没有 `B921600` 常量，必须走 ioctl，实测配不上）。

---

## 5. ESP-IDF 的 `install.sh` 在 macOS 上不带 cmake/ninja

`./install.sh esp32s3` 只装编译器工具链，cmake 和 ninja 需要自己 `brew install cmake ninja`，否则 `idf.py build` 报 `"cmake" must be available on the PATH`。

## 6. GT911 的地址**不要写死**（我一开始就记错了）

冷启动扫总线扫到 GT911 在 **0x14**，于是写进了 `pinout.md`。
后来真去读产品号，报 `ESP_ERR_INVALID_STATE`——实际这块板子上它在 **0x5D**：

```
I (2687) touch: GT911 就绪，产品号 911 @0x5D
```

原因：**GT911 的 I2C 地址由复位时 INT 引脚的电平决定**，0x5D 和 0x14 都是合法值，
取决于谁、在什么时候把它复位过。出货固件用的就是默认的 0x5D。
我那次扫描是在工厂固件刚跑过之后做的，读到的是另一种复位结果。

**结论：这颗芯片的地址是时序的函数，不是板子的常量。** 正确做法是
`i2c_master_probe()` 逐个探 0x5D / 0x14，探到谁用谁；探不到就把整条总线扫出来打日志。
写死任何一个都会在某次上电顺序变化后失效，而现象只是"触摸没反应"，
很容易误判成手势逻辑写错。

QMI8658 则确实是非默认的 **0x6B**（常见默认 0x6A）。

## 7. 旧版 eFuse 对照表会误判 PSRAM

用 `PKG_VERSION=0` 查旧表会得到"无内置 PSRAM"的结论，**是错的**。
以 esptool 5.x 的特性检测为准：`Embedded PSRAM 8MB (AP_3v3)`，实际是 octal、80MHz。

---

## 8. 全屏清屏是帧耗时的大头

480×480 全屏清一次约 **26.8 ms**，直接把帧率钉死在 30fps 以下且没有余量。
改成只清精灵的**脏矩形**后降到 **12.9 ms**（2.1 倍），留出 20ms 给文字和限额条。

背景只在启动时铺一次；注意双缓冲下**两个缓冲都要铺**，否则第一次交换会闪一帧脏数据。

---

## 9. 串口突发丢帧：UART 中断必须放进 IRAM

**现象**：单帧从不出错，但主机一次性连发 6~7 帧（resync 场景）时，板子收到的是**两帧粘连且中段缺失**的行：

```
{"e":"session","id":"1e0508b1","name":"aiagent-4f","status,"name":"clawd-hardwar
```

表现在界面上就是：项目名一直空白、Week 和 Fable 没数据——因为这几个字段恰好都在较长的帧里，最容易被截断。

**原因**：渲染循环每秒 30 次密集读写 PSRAM，cache miss 期间**非 IRAM 的中断处理会被延迟**，UART 硬件 FIFO（128 字节）来不及排空就溢出丢字节。

**解法**：`CONFIG_UART_ISR_IN_IRAM=y`。加上后项目名和 Week 立刻恢复显示，丢帧率明显下降。

**但 IRAM 只解决了一半。** 剩下的个位数丢帧靠三件事一起收干净，缺一不可：

| 改动 | 位置 | 理由 |
|---|---|---|
| 帧间隔 15ms → **40ms** | `host/src/serial.ts` | 决定性的一条。见下 |
| RX 环形缓冲 2048 → **8192** | `firmware/main/link/link.c` | 要能吃下**一整轮 resync 的突发**，而不是刚好装下一帧 |
| 链路任务钉到 **CPU1** | `xTaskCreatePinnedToCore(…, 1)` | 渲染循环在 CPU0 密集读写 PSRAM，同核会把链路任务饿住 |

**帧间隔是主因，而且它的症状极具误导性。** 丢的总是突发里**靠后**的那几帧，
而 `mlimit`（Fable）恰好排在 `hello` + 一串 `session` + `limits` 之后——
于是表现为"Fable 这个功能坏了"，让人一路去查限额解析、`~/.claude.json`、
渲染分支，全都没问题。**实际是排在队尾的帧被突发打掉了。**

实测对照（同一组 27 帧、3 轮 resync 突发）：

| 帧间隔 | 稳态丢帧 |
|---|---|
| 15ms | 40 秒内个位数，且集中在队尾 |
| **40ms** | **0** |

代价为零：一帧约 100 字节，40ms 仍支持 25 帧/秒，而实际每秒最多几帧。
**宁可慢一点，也不要发出去的是坏帧。**

## 10. 不要给 tty 的 writeSync 加"短写重试"循环

看起来是好习惯，实际是灾难。tty 的 `writeSync` 会返回一个**偏小的字节数、但数据其实已全部写出**，按返回值补发剩余部分会把尾部重复一遍：

```
{"e":"ctx","id":"dfc3f9ef","pct":73ct":73}     ← 尾巴重复
```

好帧被改成坏帧，丢帧计数从个位数涨到 133。**一次 `writeSync(fd, line)` 写完即可。**

---

## 11. Fable（按模型细分的额度）没有实时来源——已放弃

想在板上显示 Fable 的周额度，把三条可能的来源全查穿了，结论是**做不到实时**：

| 来源 | 有 Fable？ | 新鲜度 | 额外请求 |
|---|---|---|---|
| statusLine 的响应头 | ❌ **头里根本没有** | 实时 | 无 |
| Claude Desktop 采样 | ❌ **只有两个字段** | 1 分钟前 | 无 |
| `~/.claude.json` 的 `cachedUsageUtilization` | ✅ 有 | **24.6 天前** | 无 |
| 自己调 `/api/oauth/usage` | ✅ | 实时 | **有 —— 红线** |

逐条的实证：

**响应头里没有按模型细分的桶。** 对已安装的二进制逐字符串计数：

```
unified-5h-utilization : 2 处    ← 有
unified-7d-opus        : 0 处    ← 无
weekly_scoped          : 2 处    ← 只出现在 /usage 的响应体解析路径里
```

**Desktop 的采样也没有。** `plan-usage-history.json` 里 4506 个样本，
字段集合只有 `t / org / u.fh / u.sd`——五小时和七天两个数，没有任何模型维度。

**唯一有 Fable 的是 CLI 自己的 `/usage` 缓存，而它只在你手动开 `/usage` 时才刷新。**
`~/.claude.json` 这个文件本身一直在被改（mtime 是几分钟前），
但 `cachedUsageUtilization.fetchedAtMs` 纹丝不动停在 24.6 天前——
**新开会话不会刷新它**，别被文件 mtime 骗了。
所有 `/api/oauth/usage` 的调用点都是用户动作触发的 UI 流程，没有任何定时器。

> ⚠️ 排查时最大的弯路：一直以为是限额解析或渲染有问题。
> 实际上主机侧从头到尾都在正常发 `{"e":"mlimit","name":"Fable","pct":16}`，
> 板子也能正确显示——**它显示的就是三周前那个数**。
> 数据没错，错的是它的年龄。

**决定：拿掉这一行。** 一个看起来实时、实际过期三周的数字比空着更糟；
而要它变准就只有自己发请求，那是不能碰的红线。底部改为三条：5h / Week / Context，
条子加厚、行距拉开，占满原来四条的竖向范围。
